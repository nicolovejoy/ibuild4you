# Data model

Firestore collections: fields, limits and history. Moved out of `CLAUDE.md` on 2026-11-18, word for word, to keep that file short. `CLAUDE.md` keeps a one-line summary of each.

- **users** — identity (email, first_name, last_name), auto-populated from Google sign-in
- **approved_emails** — per-email approval record, keyed by normalized email. **Not the sign-in gate** (Garm is, since PR G) except on a preview deployment with no Garm wiring. Still live as an *input* to the Garm grant (dual-write + hourly reconcile): an approved email with no brief gets a viewer grant, and `revoked_at` (off-boarding, #163) drives the revoke. Writers validate address shape (`isValidEmail`, PR H).
- **project_members** — role-based membership (owner, builder, apprentice, maker); makers sign in with Google or a password-setup link (passcodes retired, PR D). Nobody can invite, re-role, remove, restore or re-key onto their own row (`selfEditError`/`isSelfRow` in `lib/members/`, #245); your own People row is read-only.
- **projects** — one per maker engagement, includes agent config (session_mode, directives, opener), requester name/email, tracking fields (shared_at; the builder's reminders to the maker as `last_nudged_at` (the latest of an email or a copy) + `last_nudged_method` (`email` or `copy` for that latest one) + `last_nudged_to` + `last_nudge_emailed_at` (the last email: its addresses and its time), all server-written: `PATCH /api/projects` with `last_nudged_at` stamps method `copy` and the server's time, not the browser's, and leaves `last_nudged_to` and `last_nudge_emailed_at` alone, so a copy never hides the last email; the project email route stamps all four, with method `email` and the addresses it really went to, for kinds `reminder` and `nudge`; a missing method means recorded before 2026-11-23; a project stamped before `last_nudge_emailed_at` existed uses `last_nudged_at` as the email time when the method is `email`; a send suppressed on preview records nothing; `latest_session_created_at` is also stamped by an import that posts a welcome into an open conversation, to restart the automatic-reminder cadence (the name is historical; the project list keeps the later of it and the newest session start); `last_reminder_sent_at` is the automatic reminder, written by the cron and nulled by every maker message because the cadence needs that; `last_auto_reminder_at` is written with it and never cleared, and the builder's reminder line reads it, falling back to `last_reminder_sent_at` for reminders sent before it existed), `maker_waiting_since` (server-written by kickoff when it posts the nothing-queued greeting; cleared by the next maker turn or by an import; drives the builder's "Maker waiting" dashboard state), `thumbs_down_count` (Sam's replies with a 👎, kept by `PATCH`/`DELETE /api/messages` with increments so the dashboard list needs no extra reads; prod had no 👎 when it shipped on 2026-11-03, so no backfill ran; `scripts/backfill-thumbs-down-count.mjs` recounts if ever needed).
- **sessions** — each conversation between maker and agent, snapshots agent config at creation
- **messages** — individual messages within a session, role (user/agent) and timestamp, optional file_ids. Optional `kind`: `unqueued_greeting` (the canned nothing-queued note, set by kickoff, removed by import) and `welcome` (a builder welcome an import posted into an open conversation; a welcome posted at session creation carries no `kind`). Agent messages may carry the maker's `rating` (`up`|`down`, #130) and, on a 👎, an optional `rating_reason` ("what was off?", ≤500 chars) via `PATCH /api/messages`; any other rating clears the reason.
- **files** — uploaded files (metadata in Firestore, bytes in S3 at `ibuild4you-files` bucket), scoped to project
- **apps** — Loop host apps, doc id = slug (`name`, `github_repo`, `feedback_requires_identity`, `brief_id`, `legacy_slugs` = ids widgets still send, `created_by` provenance only, timestamps). Settings only. Since Phase B an app's admins live only in Garm (owner/collaborator grants on the app slug), read live through Loop's key (`GARM_LOOP_KEY`, `lib/garm-loop.ts`) on every request; nothing about them is stored or cached locally. Ingest resolves a canonical or legacy slug and stores the canonical one on `feedback.project_id`; signing secrets are `loop_signing_secrets/{slug}`.
- **briefs** — living brief for a project, structured and versioned; the comms agent curates it at each paste and the app writes a note after each conversation. Since #194 every overwrite archives the outgoing version to `briefs/{id}/versions/{version}` (`{version, content, updated_at, source, archived_at}`, no cap) and the live doc carries `source` (`create`|`paste`|`regen`|`restore`); `GET /api/briefs/versions` lists them (builder+). Since #229 the app no longer rewrites the brief after a conversation: a `briefs/{briefId}/notes` subcollection holds one short note per conversation stretch (written by the notify cron or the Brief tab's "Write note now", `lib/api/note-writer.ts` / `lib/api/brief-notes.ts`; `folded_at` is set when a curated paste folds it in), `projects.notes_through_at` marks how far notes cover (it is the only thing that marks a stretch as read: a stretch with nothing relevant to the brief writes no note, and only `notes_through_at` moves; the writer logs one `brief.note_empty` line with the project id and the count covered, and the Brief tab's "Write note now" then shows "Nothing relevant to the brief was said since the last note, so no note was written." when the API answers `note_id: null`), and a confirmed maker reversal of a locked decision sets `contested` at note time as a version with `source: 'note'` (sources are now `create`|`paste`|`restore`|`note`), and the Brief tab's History → Restore re-submits one through `PUT /api/briefs` with `source: 'restore'`. `open_risks` elements are `string | { text, owner }`. A note carries `made_from` (`chat` | `email` | `both`, #276), stamped by code from the window it read and never by the model: any chat message counts as conversation whoever wrote it, and an email counts only if it still had text left, the same rule as `email_sources`. The Brief tab heads a note "Conversation of …", "Email of …" or "Conversation and email of …" from it, and so does Sam's prompt (`### …`); both read it through `noteSource` in `lib/brief/note-source.ts`, which for a note written before the field falls back to `email_sources` and `session_id` (it can read "both" as "email" when the chat sat in an archived session). The model sees a required boolean `nothing_new` on the `write_note` tool; code drops the text only when it is the boolean `true` and the note has no decision, no risk added, no risk settled and no lock reversal that survives (a reversal from a window with no maker chat turn is cleared first and does not count). A 👎 keeps the note, with empty text. `nothing_new` is never stored. A note's `risks_resolved` elements are `string | { text, resolution }`: since 2026-11-15 the note writer records what the maker said that settled the risk, and the prep tells the comms agent to write that answer into the brief before dropping the risk (`resolvedLine` in `lib/brief/risks.ts`). Content may also carry optional `shipped` `[{date, items}]` (dated batches of what went out) and `queued` `[string]` (what is next, not built) (#219).
- **reviews** — builder annotations on a brief, feed back into agent context for next session
- **garm_denials** — counts-only record of sign-in denials keyed by sha256(email); kind unknown-principal | known-member (lib/garm-denials.ts). No addresses stored. The hourly garm_reconcile_log row carries 24h counts of each.
- **loop_read_keys** — one per Loop app, doc id = canonical slug: `{ key_hash (sha256 hex), created_at, created_by, last_used_at? }`. The key itself is shown once at mint on `/admin/apps/<slug>` (system admin) and never stored. Used by `GET /api/feedback/read` (contract `lib/feedback/READ.md`).
- **build_status_keys** — one per build repo, doc id `owner__name`: `{ repo, key_hash (sha256 hex), created_at, created_by, last_used_at? }`. The key (`bsk_…`) is shown once when a system admin mints it on the Settings tab (Connections, beside the GitHub repo) and never stored. It belongs to the repo, so two briefs on one repo share it. It can add a build report through `POST /api/build-status` and nothing else. Mint, check and revoke: `/api/build-status/key`.
- **projects/{id}/build_reports** — status reports Claude Code in the build repo posts with that key: `{ repo, brief_version_checked, live [{what, checked, try_it?}] (`try_it`, optional since 2026-11-21: what the maker can do to try the item; the prep shows it as "maker can try"), merged, proposed, questions, posted_at, body_hash, folded_at }`; `folded_at` is stored as `null` until a paste folds the report. `live` is only what was checked in production. Limits: 30 items per list, 500 characters per string, 4,000 in total; a report identical to the project's latest report (same lists and brief version) within ten minutes is a duplicate (200, nothing stored); a project already holding 50 unfolded reports takes no more (429) until a paste folds some. Deleting the project deletes them. `GET /api/build-status` (builder+) lists the unfolded ones; "Copy next-convo prep" puts them in a `<build_status>` block (cap 15,000 characters, oldest left out first) and lists every id in the stamp's `report_ids`; a stamped paste sets `folded_at` on exactly those. Reports never make a prep stale.
- **project_emails** — mail sent to a project's email address by one of its members (email-in, 2026-11-20). Doc id `<resend email id>_<project id>`, so one email that names two projects is stored once for each: `{ project_id, from_email, from_name, from_role ('maker' | 'builder'), received_at, sent_at, subject, message_id, text, truncated, attachments [{filename, content_type}] }`. `from_name` and `from_role` come from the member row, never from the email. `text` is cut at 50,000 characters (`truncated: true`); attachments are names only, no bytes. Written only by `/api/webhooks/resend/inbound` after the sender check (`lib/email-in/sender.ts`: the From header must be a member's address and DMARC must be `pass`); a project takes at most 50 a day. No client rule. Deleting the project deletes them. On the project: `email_in_address` (minted once by `POST /api/projects/email-in`, never changed; the mint also sets `notes_through_at` when it is unset, to the brief's `updated_at` or to the epoch value when there is no brief, so a later brief save cannot move the note writer's start past a stored email), `last_email_at` (the `received_at` of the last stored email, which is the app's clock at storing and not Resend's time; the notify cron's second trigger), and `email_in_dropped { not_member, auth_failed, over_limit, last_at, last_auth_failed_from }` (counts of refused mail; an address is kept only for a member's address that failed the sender check). The note writer reads these emails with the chat messages as one stream ordered by time, each read once by `lib/email-in/reading.ts`: code credits every quote to its author, and lines the app already holds come back only as context around new lines (typed lines are always kept; an email that repeats an earlier one from the same sender is left out whole); a note that covered emails carries `email_ids`, `email_sources [{from_name, from_role, received_at}]` (only emails that still had text) and, when one email was too long to read whole, `email_truncated`; every note carries `made_from` (see **briefs**). A stretch of emails with nothing relevant writes no note, so nothing records which emails it covered. The address never sends anything.
- **integration_groups / integration_participants / integration_messages / integration_ops** — stars-demo round-two group conversations, server-to-server only (contract `/Users/nico/src/stars-demo/docs/specs/08a-ibuild4you-contract.md`; plan `docs/superpowers/plans/2026-09-22-stars-demo-round-two-integration.md`). Separate top-level collections on purpose: the client-readable `messages` rule, admin implicit-owner, brief regen, dashboard enrichment and the notify cron never see them. Messages carry an opaque `author_id` + `author_label`, never email or name. Routes under `app/api/integrations/stars-demo/*`, auth in `lib/api/integration-auth.ts`, store in `lib/integration/`.
