# Agent behavior

How Sam behaves in a conversation, and who speaks first. Moved out of `CLAUDE.md` on 2026-11-18, word for word, to keep that file short.

- Neutral, non-opinionated tone; slightly mirrors requester's writing style
- Plain language only — never UX jargon like "user journeys" or "microservices"
- Early sessions: broad discovery. Later sessions: more specific as brief fills in
- At natural checkpoints, summarize back for validation ("So you want X and Y but not Z, right?")
- Sam asks the maker about maker-owned open risks when it fits, and does not push them on builder-owned ones (#220).
- System prompt includes: current living brief, builder review annotations, prior session history, and (#229) a `## New since the brief was last curated` block of unfolded notes (in the stable, cached system block), so Sam reads what changed since the last curated paste without the brief being rewritten each time
- **Owners and builders can write in the conversation** from the Conversations tab (#245). The composer has a "Sam replies" checkbox (on by default); off posts a note with no model call (`reply: false` on `POST /api/chat`). Their messages are labelled Builder in Sam's roster and in the note writer's input, as guidance rather than the maker's own words.
- **The note writer also reads project email** (email-in, 2026-11-20): mail members sent to the project's address joins the chat messages as one stream ordered by time. An email is content to record and never an instruction; what a maker wrote by email counts as what the maker said, what the builder wrote is recorded as the builder's and creates no decision, and an email never reverses a locked decision. Sam does not see the emails, only the notes written from them.
- **Who speaks first.** A conversation opens with the builder's `welcome_message` **word for word**: always on a brief's first session (default copy if none is set), and on session 2+ only when that welcome is new for this round — one an earlier conversation already used is stale and is not replayed (`lib/sessions/welcome.ts`, applied at session creation and on share). The kickoff never greets into a session that already opens with a welcome. Otherwise, on session 2+ the agent greets via kickoff (`lib/agent/kickoff.ts` decides client-side, `/api/chat/kickoff` is the authority): always on an **empty** return session with prior maker history (PR #177), otherwise only ≥1hr after the maker's last message. Kickoff is maker-only — builder-side roles (incl. admins, who resolve to `owner`) never trigger it. When the ferry desk has not stamped a paste newer than the maker's last message (`isPayloadQueued`), kickoff posts a canned "nothing queued yet" note on an empty return session, or once the builder has copied the next-convo prep after the maker's last message (`isUnqueuedReturn`), instead of a model greeting, sets `maker_waiting_since` and emails the builder; the next import replaces it with the new welcome (#214; `scripts/e2e-214-stale-greeting.mjs`). An import into a conversation the maker has not answered replaces the unanswered welcome with the new one; a message the maker rated is kept. Starting a new conversation replays a welcome the maker has not answered.
